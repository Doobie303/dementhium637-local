## Testing policy — scope checks to the change

The owner explicitly requests relevant testing rather than automatically rerunning every accumulated suite. Read `tests/TESTING.md` when selecting validation. Test changed behavior and realistically affected callers; a shared filename, shared class or feature label alone does not justify a suite. Inspect the actual methods/data contracts that changed. Start with the smallest meaningful regression, add connected integration coverage when warranted, and broaden only for a concrete dependency, failure or unresolved risk. Once appropriate checks pass, stop testing unless subsequent changes justify more checks. Documentation-only changes do not require gameplay regressions.

Historical reports listing all-suite passes and old build/verify/stage scripts are records of those releases, not minimum requirements for future fixes. New batch runners and staging gates must use that batch's justified selection, not copied cumulative suite counts. Preserve existing tests for when relevant; remove unrelated suites from the current run, not from the repository. Report which checks ran, what they cover and any material untested boundary. Full compilation and a full behavioral test run are separate decisions. Preserve required runtime backups/hash checks and relevant live acceptance.
