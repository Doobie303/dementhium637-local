# Duel Arena fixes and acceptance — 2026-09-08

The owner authorized implementation of the findings in DUEL_ARENA_2011_REVIEW.md. That document remains the historical review; the current implementation is described here. Active source is `src`.

## Implemented

- **One duel owner and explicit terminal states.** A duel reserves both participants immediately, owns both stake containers, records a single result and cancels its countdown/death tasks on exit. Repeated death, departure, decline, shutdown and result calls cannot pay twice. There is no delayed callback that saves a disconnected player. Original retained/aggregate stake ownership and the `duelStake`/`duelStakes` mismatch were removed.
- **Exact stake transfers.** Addition/removal validates the slot, item, quantity and metadata, prepares the destination before committing, and rolls back on save failure. Notes, full offers, maximum stacks and charge/degradation values are preserved. Friendly duels reject all stakes. The generic legacy removeItems helper is no longer used as evidence that an item was debited.
- **Durable recovery.** Each successful offer change saves inventory and recoverable escrow together. An optional `DUL2` trailer stores item IDs and complete packed amount/charge hashes. It is omitted when empty, retaining the previous layout for ordinary accounts. On login, unfinished escrow becomes unclaimed items; saved duel positions use the challenge room. Winners/refunds are credited through the same storage. Items that cannot fit remain saved and can be collected using `::duelclaim`; they are never dropped as an overflow fallback.
- **Atomic settlement journal.** A two-account redo journal records both complete account post-images before installation. Atomic replacement and file flushes protect each image. Recovery runs before profile reads/writes and replays both images idempotently after an interrupted installation. A failure before journal commit leaves the duel's escrow owned and retryable; a committed journal remains authoritative even if account-file installation must be retried. Normal profile saves also use atomic replacement.
- **Autosave and login ordering.** Profile snapshots synchronize with the world-cycle monitor. Closed or superseded Player objects cannot overwrite active accounts. Loaded profiles carry a digest which is checked before registration, preventing a preloaded stale image from entering after an intervening save. Duplicate active registration is rejected; ordinary lobby-to-game transfer is retained, retiring the old lobby object's ability to save.
- **Versioned consent.** Every actual rule/stake change invalidates both accepts. Both final accepts refer to a frozen revision, exact stake snapshots and a rule snapshot. A three-tick (1.8-second nominal) review delay applies after changes and on entering final confirmation. Stale X prompts bind to duel identity, revision, slot, item and packed metadata; they cannot mutate another duel or later offer.
- **Visible warnings and names.** Rule edits show both participants an explicit ON/OFF change message, including automatically changed dependent rules. Rule labels highlight red; the correct first-screen status field (631:26) is cleared/replaced. Names and levels are sent after opening interface 631. Confirmation identifies the opponent and mode, shows exact quantities in the actual scrollable stake-text components (626:46/47), and correctly handles empty stakes. Before/during rule text uses bounded, verified fields; the staking inventory panel closes at confirmation.
- **Rules enforced.** No Forfeit is checked at both trapdoor and confirmation. Fun weapons enforce an explicit whitelist (rubber chicken 4566, flowers 2460–2468, mouse toy 6541) at acceptance, equip and combat dispatch; bare hands, regular weapons and non-melee attacks are rejected under that option. Contradictory unfinishable combinations are rejected. No Shield removes an already-equipped two-handed weapon and still prevents re-equipping one. Both players' equipment-removal capacity is checked again immediately before starting.
- **Admission and mode.** Requests retain the source/target Player identities, selected friendly/stake mode and 100-tick expiry. Arrival revalidates both players' session identities, availability and challenge-room presence. Busy participants, stale indices, expired requests and overlapping third-player challenges are rejected. Friendly mode uses the verified rule interface with explicit no-stake messaging rather than guessing different interface wiring.
- **Safe start/end boundaries.** Actual arena landscapes load before choosing walkable starts. No Movement chooses adjacent open tiles; no valid start triggers a refund. Negotiation, accepted-but-not-started, countdown, fighting, death animation and settling all have refund/settlement paths. Both participants return to the challenge room. Used recoverable ammunition is consumed from its record once; its container grows safely rather than overflowing.
- **Duel-owned death and pending combat.** The lethal hit locks the result without immediately restoring HP, preserving damage/XP accounting. The duel owns the death animation delay. Later death or departure cannot change the chosen winner. Pending actions are cancelled on start/end; typed Damage captures duel ownership as well as instance revision, rejecting hits from a previous duel after departure. Duel deaths bypass ordinary grave/PK-death processing. Godmode and personal XP calculations remain.
- **Audit trail.** `duel-results.log` in the configured player-save directory records timestamp, duel ID, winner/refund, both account names and exact ID/quantity/charge stakes. It contains no passwords. The result interface is display-only; payment is already durable and its button reads Close, avoiding a second claim authority.

## Historical and policy boundaries

The target remains provisional 2011 pre-EoC. The original review's references support the historical two-stage arena flow, not every UI or anti-scam timing detail. The 1.8-second review gate and explicit red change descriptions are deliberate safety enhancements, not a claim of exact 2011 warning graphics. Cache inspection verifies the shipped server-cache component layout; live rendering, script timing, wrapping/scrolling and the external client's cache match still require acceptance.

The fun-weapon list is deliberately explicit, not a claim that every period novelty item is certified. Its IDs/names are checked against the packed definitions. The older arena guide identifies rubber chickens as a fun-weapon example; later reference lists also identify flowers and mouse toys. No modern EoC items, taxes or stake caps were imported.

First lethal impact locks the winner. A disconnect during that death animation cannot turn a win into a refund/loss. An ordinary live-fight disconnect forfeits; a pre-fight negotiation departure refunds. Administrative abort/shutdown refunds unless a death/winner has already been chosen, in which case that result is completed. Both-account installation is crash-recoverable; a crash before a result is durably committed recovers each account's own saved escrow. This is a documented interruption policy, not certification of Jagex's proprietary double-KO/restart policy.

Summoning-specific mechanics and Dungeoneering remain deferred. Existing Summoning rule selection was retained, but familiar AI/specials are not certified or expanded by this batch. Godmode, personal XP rates, custom PvP EP/rewards, Barrows boosts and unrelated workspace changes are preserved.

## Duel warning UX follow-up - 2026-09-09

The owner reported noisy feedback on every checkbox change and warnings disappearing on hover. Actual client Class293 decoding (build/duel-warnings/hooks.log) confirms the option enter/leave hooks call script 68 with target 41353242 = 631:26 and either help text or an empty string. The former warning/acceptance bottom line is therefore client-owned hover help, not a persistent warning surface. The 631:92 Accept label has color-only hover hooks (script 45), not the help-text replacement.

Implemented in DuelActivity and DuelConfigurations:

- Initial setup is quiet: before either player first accepts, rule/stake edits update controls without warning chat or red highlights. The existing three-tick acceptance delay still applies to every edit.
- After acceptance has begun, any rule or stake change clears both accepts and sets a persistent amber Review label on both players' Accept buttons. It remains until that viewer accepts the current revision. Accepted also appears on that viewer's button, independently of transient hover help.
- Changed text rules accumulate red asterisk markers until each viewer accepts, including automatic dependent-rule changes and toggling a rule back. Markers mean edited since review, not necessarily a net difference. Equipment changes also trigger Review and explicit opponent chat; equipment icons have no added text marker.
- Changed stakes mark the appropriate Your stake/Opponent's stake heading for each viewer. New duels initialize all labels/headings/button state to avoid stale cached markers.
- Self-edit chat is emitted only when an edit actually clears an acceptance. Subsequent edits do not repeatedly announce that the player changed their own setup. The opponent receives concise post-consent details using allowed/blocked or enabled/disabled wording, rather than ambiguous No Food OFF. Initial setup emits neither message.
- The bottom line is cleared on edits and remains available for normal hover help. Existing bottom-line acceptance text can still be replaced by hover, but the persistent button state carries the consent status. Final confirmation and its review delay are unchanged.
